# TP8 持续到达负载：探索进展

当前插件改善了部分负载下的 decode 停顿和请求 goodput，但尚未证明比经过
调优的原生 vLLM 有更高的持续吞吐或容量。高负载下，缩短 P 切片会增加
推进与提交开销；现有 P/D 重叠还不足以抵消这些代价。

本文记录探索结果，不替代独立 seed 的确认实验。早期固定队列的
[争用报告](performance-tp8-contention.md) 使用另一种负载和统计口径，
不能与下面的持续到达结果合并。

## 同条件 OMP1 对照

模型为 Qwen3.5-35B-A3B BF16，8 张 910B2，TP8/EP8，maxseq8，
关闭 prefix caching。原生使用 async scheduling、16K token budget 和
FULL_DECODE_ONLY；插件使用独立通信组的 D-first overlap、D graph，
有 D 同轮推进时 raw P 固定四层切片。双方使用 OMP1。

每档重放同一 seed101 Poisson 到达计划，20 秒连续暖场、60 秒到达窗口，
按 80%/20% 的概率分别抽取 128→256 和 12000→8 token 请求。每个配置的六档共
490 个请求均完成，并通过独立原始 SSE 重放审计。

| 目标到达率 /s | 原生 / 插件 tok/s | 原生 / 插件 gap P99 ms | 原生 / 插件 TTFT P99 s | 原生 / 插件严格达标请求数 |
| --- | ---: | ---: | ---: | ---: |
| 0.25 | 68.58 / 66.52 | 16.11 / 47.39 | 0.508 / 0.549 | 9/18 / 18/18 |
| 0.5 | 137.17 / 137.00 | 350.97 / 53.06 | 0.650 / 0.842 | 5/38 / 38/38 |
| 0.75 | 179.83 / 182.63 | 352.72 / 61.82 | 1.836 / 2.786 | 5/46 / 37/46 |
| 1.0 | 219.38 / 220.72 | 373.32 / 58.80 | 2.429 / 15.238 | 5/59 / 22/59 |
| 1.5 | 279.03 / 245.68 | 354.89 / 57.86 | 11.597 / 47.318 | 0/93 / 7/93 |
| 2.0 | 276.10 / 251.67 | 370.04 / 56.56 | 42.473 / 68.616 | 0/120 / 4/120 |

严格达标要求每条测量请求的计划到达 TTFT≤1s，且完整请求的**每一次**
单 token gap≤100ms；对应 goodput 为达标请求数除以 60 秒。表中 gap P99
则合并所有测量请求的完整相邻事件间隔，两者不能互换。tok/s 只统计固定
窗口内实际收到且最终传输有效的输出，包含暖场请求落入窗口内的输出。
低负载下小幅 tok/s 差异可能来自窗口边界。

例如 0.5/s 下插件严格达标 38/38，原生为 5/38，说明此配置与这条探索
trace 下已有 goodput 改善信号。但在 1.5/s 下插件吞吐低约 12%，TTFT
也明显变长；其 backlog 从 15 增到 34，2/s 下从 29 增到 78。
gap P99<100ms 本身不代表可持续容量。尚未完成原生调优或 held-out 确认。

双方整个测量控制器期间的 cgroup `nr_throttled`、`throttled_usec` 增量
均为 0，不能把这些结果归因于已经观察到的 CPU 配额限流。该快照包含
priming、暖场、测量、排空及间隔，不是单个请求或单卡的耗时分解。

## 小 token budget 对照的失败结果

原生 async OMP1 保持上述条件，仅将 token budget 从 16K 改为 512，
仍只捕获 decode graph。已尝试的五档均完成原始证据重放，结果如下。

| 目标到达率 /s | tok/s | gap P99 ms | TTFT P99 s | backlog 起→止 | 完成情况 |
| --- | ---: | ---: | ---: | ---: | --- |
| 0.25 | 54.90 | 387.32 | 9.060 | 0→7 | 完成 |
| 0.5 | 115.77 | 376.65 | 15.601 | 1→13 | 完成 |
| 0.75 | 115.65 | 354.73 | 32.751 | 4→20 | 完成 |
| 1.0 | 107.48 | 358.26 | 83.785 | 12→42 | 完成 |
| 1.5 | 123.72 | 357.11 | 135.706 | 20→79 | 排空超时，无容量比较资格 |
| 2.0 | — | — | — | — | 按失败停止规则未运行 |

1.5/s 档的 122 条计划请求（含暖场）中，84 条完成，38 条在规定的
120 秒排空期限结束时取消。失败请求保留在分母中，失败档的百分位仅描述
已观察到的首 token 和相邻事件间隔，包含不完整响应的已观察部分，不代表
全部请求。没有重试、补齐或将其算作成功容量。
此配置并未改善高 gap；缩小 chunk 不能代替减少单次执行的固定开销。

## 当前瓶颈与下一步验证

已有独立诊断在 work-token budget 262144 下观察到 P12000 按 21+19 层
推进。八个 rank 可见的 P/D 计算交集只占所选计算区间并集约 2.02%–2.26%。
这是带 profiler 的执行顺序诊断，不能当作上述固定四层切片的性能分解。
P 主机提交段结束之前，本轮 D 的原生采样、输出与下一轮推进仍受阻。
独立通信组也不等于论文中的计算资源划分。

主机区间还包含运行时提交、通信与依赖等待，不能全部归为可消除的 Python
开销。当前正在分别验证提前提交 greedy 采样/D2H、短 P 编译执行和短 P
PIECEWISE 图路径；这些实验功能默认关闭，尚无实机收益结论。

公平基线还需覆盖原生 FULL_AND_PIECEWISE：此前 1/2/4/8 的 capture
档位只覆盖 decode，不能代表原生 prefill 图能力。已提前登记 512/1024
预算与对应 P 档位。512 配置已完成独立诊断：八个 rank 均观察到 P128、
P129、长 P 分块、实际 P+D mixed 的已有图重放和 D FULL 对照，未观察到
服务阶段首次 ACL 图捕获或图调用失败；这是主机调用路径证明，不是设备
重叠或性能结论。自然语言 16/16 文本一致，取消后新请求完成。

状态探针中的一 token 提示和部分合成序列仍有重复不稳定，全部保留；不能
将传输检查通过当作数值等价。独立检查器初版遗漏了原生 engine ID 的随机
八位后缀，按固定原生源码修正后通过；原始回执和初版失败结果未覆盖。
